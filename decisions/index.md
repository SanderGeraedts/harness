# Global decisions

These hold in every project that installs the harness, unless the project overrules one
(G-0002). Read this list first, then the project's own index, then only the records your
work touches. How the registries work is in [README.md](README.md).

## Accepted

### Way of working

- [G-0001 Decisions live as files in two registries: a global one in the harness and one in each project](G-0001-decisions-live-in-two-registries-global-and-per-project.md): Every lasting choice is a file: G-NNNN in the harness for what holds in every project, D-NNNN and Q-NNN in a project for what is specific to it; decisions are replaced, never edited.
- [G-0002 A project may overrule a global decision with its own decision that names it](G-0002-a-project-may-overrule-a-global-decision-by-naming-it.md): A project decision with overrules: [G-NNNN] and the reason sets that global decision aside for that project; harness overrules lists every overrule and harness check verifies the ids.
- [G-0003 Personal details may be redacted from records in place; what was decided never changes](G-0003-personal-details-may-be-redacted-in-place.md): Names of people, employers and private details can be removed from decisions, questions, tasks and docs without a replacing record, as long as the substance stays the same; the redactions are listed in the pull request.
- [G-0004 Projects install the harness as a pnpm dev dependency from GitHub, pinned by tag](G-0004-projects-install-the-harness-as-a-pinned-dev-dependency.md): A project adds the harness with pnpm add -D github:SanderGeraedts/harness#vX.Y.Z; rules and global decisions are read from node_modules, scripts run through the harness bin, and CI and auto-merge call its reusable workflows at the same tag.
- [G-0005 A harness update lists every new or changed global decision, and the architect conforms or overrules](G-0005-a-harness-update-lists-the-changed-global-decisions.md): The pull request that bumps the harness in a project carries the output of harness changes <from> <to>; per decision the project's architect opens a task to conform or records an overruling decision.
- [G-0006 A new global decision is recorded in the project first and proposed to the harness, where it waits for the Engineer](G-0006-new-global-decisions-start-in-a-project-and-wait-for-the-engineer.md): A choice that would suit every project is recorded as a project decision so work continues, and the architect proposes it by pull request on the harness; there, a pull request that touches the global registry waits for the Engineer and every other green one merges itself.
- [G-0007 There are two human roles, Engineer and Requester, told apart by the signed-in GitHub account](G-0007-two-roles-engineer-and-requester.md): The Engineer makes the architectural decisions that need a human; anyone else is a Requester, who asks for changes and is never asked engineering questions; .harness/engineers lists the Engineers' GitHub logins and harness role prints which one the session is talking to.
- [G-0008 A team of four agents works each task as a pipeline: architect, UX designer, developer, tester](G-0008-an-agent-team-works-each-task-as-a-pipeline.md): Each task passes from the architect to the UX designer (for anything visible), the developer and the tester; each writes its result in the task file, the developer builds in a draft pull request, and only the tester marks it ready, so nothing merges untested.
- [G-0009 Agents may do anything that can be reversed; anything irreversible or that costs money needs a human](G-0009-agents-do-what-can-be-reversed-a-human-decides-the-rest.md): Agents may record decisions and merge green pull requests; what can't be reversed or costs money needs the Engineer for technical matters and the Requester for their own content, and irreversible includes deleting data or backups, making private data public and sending messages to people.
- [G-0010 The Engineer is reached through an open question in the registry and a GitHub issue assigned to them](G-0010-the-engineer-is-reached-by-a-question-and-an-assigned-issue.md): When a choice needs the Engineer, the architect records an open question in the project's registry and opens a GitHub issue assigned to the Engineer; the Requester hears in plain words that this part waits, all other work continues, and the answer becomes the decision record.
- [G-0011 Every change goes through a pull request; a green one that isn't a draft merges itself](G-0011-every-change-goes-through-a-pull-request-and-green-ones-merge.md): A green, non-draft pull request into the default branch merges itself through the reusable auto-merge workflow, and agents may merge a green one; nobody pushes to the default branch or skips git hooks, and after a backend change the workflow starts the backend publish workflow.
- [G-0012 Tasks are files with a check; their status moves in the same pull request as the work, and the index is generated](G-0012-tasks-are-files-whose-status-moves-with-the-work.md): One T-NNNN file per task with a Done-when check; status, Log and result change in the pull request that does the work, checks a human does afterwards go on a Remaining: line, a confirmation is recorded right away, and harness tasks-index generates the index that CI checks.
- [G-0013 harness waiting lists everything that waits on a human, across projects](G-0013-harness-waiting-lists-what-waits-on-a-human.md): One command lists what waits on the Engineer or the Requester: open questions, tasks' Remaining: lines and open GitHub issues assigned to them; it takes several project folders, so it shows all projects at once.
- [G-0014 Rework becomes a line in the project's lessons, and repeated lessons become proposed rule changes](G-0014-rework-becomes-a-lesson-and-repeated-lessons-become-rules.md): When a task needed rework (the tester sent it back, CI failed twice, a human corrected something) the team adds one line to docs/lessons.md; the architect turns repeated lessons into proposed rule changes for the harness.
- [G-0015 The harness tests itself by installing into a throwaway project](G-0015-the-harness-tests-itself-in-a-throwaway-project.md): The harness's CI creates a throwaway project, installs the harness into it from the checkout, and runs the harness's own checks there.
- [G-0029 New repositories start private; agents create and maintain the default branch's ruleset wherever GitHub allows one](G-0029-new-repositories-start-private-and-get-their-ruleset-when-public.md): A new repository is private by default; agents set up and keep the branch ruleset with harness protect (pull request required with 0 approvals, the CI check required, no deletion, no force-push, no bypass actors) wherever GitHub allows one, which on a free plan means from the moment the repository is public.
- [G-0030 A private project's backend image is pulled with a read-only token; a public project's image is public and needs none](G-0030-a-private-projects-backend-image-is-pulled-with-a-read-only-token.md): While a project's repository is private, the NAS pulls its backend image with a token that may only read packages, held as a fifth secret in the infrastructure environment; when the Engineer makes the repository public, its image becomes public with it and spin-up removes the token from that project's app.

### Stack for new projects

- [G-0016 pnpm is the package manager, pinned in package.json](G-0016-pnpm-is-the-package-manager-pinned-in-package-json.md): Dependencies are installed with pnpm at the version in package.json's packageManager field, with pnpm-lock.yaml as the only lockfile; npm installs are refused.
- [G-0017 A new project's front end is React, TypeScript and Vite, with TanStack Router, Tailwind, Vitest, Playwright, vite-plugin-pwa and Dexie](G-0017-new-projects-are-a-react-typescript-vite-pwa-with-dexie.md): New projects start as a static single-page app in React and TypeScript built with Vite, routed with TanStack Router, styled with Tailwind, tested with Vitest and Playwright, installable through vite-plugin-pwa, and storing local data in IndexedDB through Dexie.
- [G-0018 The backend is PocketBase on the NAS behind Tailscale Funnel; the front end is on Netlify with deploy previews](G-0018-pocketbase-on-the-nas-behind-funnel-and-the-front-end-on-netlify.md): A new project's backend is a PocketBase app on the NAS, reachable from the internet through its own Tailscale Funnel address; the front end is a Netlify site with a deploy preview for every pull request.
- [G-0019 Deploy previews and local development run on seeded demo data; only production reaches the backend](G-0019-only-production-reaches-the-backend.md): Previews and the local dev server use seeded demo data with the backend switched off; only the production build can reach the real backend, and CI tests against a throwaway one.
- [G-0020 Offline-first with sync is the default suggestion for a new project; look and language are chosen per project](G-0020-offline-first-with-sync-is-the-default-suggestion.md): For a new project the team suggests a full local copy on each device that syncs with the backend, unless that makes no sense for it; its look and its language are chosen per project.
- [G-0021 Never a UUID in a URL: addresses use readable slugs](G-0021-never-a-uuid-in-a-url.md): No address shows an internal id, in the path, the query or the hash; pages are addressed by readable slugs made from their names or dates.

### Infrastructure

- [G-0023 Each project's dataset gets automatic periodic ZFS snapshots, set up when the project is created](G-0023-each-project-dataset-gets-automatic-periodic-snapshots.md): Every project's dataset on the NAS has a periodic ZFS snapshot task from the day it is created, which replaces any manual backup before a schema change.
- [G-0026 Infrastructure secrets are held by a GitHub environment of a private infrastructure repository, and infrastructure work runs there as workflows](G-0026-infrastructure-secrets-live-in-a-github-environment-of-a-private-repository.md): The Netlify token, the Tailscale OAuth client and the TrueNAS key exist only as secrets of a GitHub environment in the Engineer's private infrastructure repository; infrastructure work runs as workflows there, started with gh workflow run from any machine, and no agent ever reads, prints or carries a secret.
- [G-0027 Agents manage the NAS only through the harness's TrueNAS tool, run by workflows on a runner on the NAS; destructive calls need a human's yes](G-0027-agents-manage-the-nas-only-through-the-truenas-tool-run-by-workflows.md): Agents manage the NAS only with harness nas, which normally runs in a workflow of the private infrastructure repository on a self-hosted runner on the NAS, with the key from the GitHub environment and a pinned certificate; destructive calls need --confirmed and a human's yes, and creating a snapshot is not destructive.
- [G-0028 One prompt spins up a new project: the repository and app locally, hosting and backend through the infrastructure workflows, by the Engineer only](G-0028-one-prompt-spins-up-a-new-project-through-the-infrastructure-workflows.md): One prompt creates the repository and the app with harness create, then starts workflows in the private infrastructure repository that create the Netlify site and, when the project syncs, a PocketBase app on the NAS with its own Funnel address and snapshot task; only the Engineer can do it, and removing a project is a separate command that asks.
