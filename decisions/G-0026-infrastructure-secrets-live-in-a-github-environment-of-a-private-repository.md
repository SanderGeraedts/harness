# Context

Creating and managing a project's infrastructure needs a hosting token, a Tailscale OAuth
client and the NAS's API key. Until now these were to live in the Engineer's environment, on
one machine at home. That ties all infrastructure work to that machine, and puts every
secret within reach of anything that runs there as the Engineer, agents included.

A workflow's run log is public when its repository is public, and infrastructure logs show
host names, network names and dataset paths.

# Decision

- **The secrets are held by GitHub, not by any machine.** They are secrets of a GitHub
  **environment** in a **private infrastructure repository** that the Engineer owns:
  - `NETLIFY_AUTH_TOKEN`;
  - `TS_OAUTH_CLIENT_ID` and `TS_OAUTH_SECRET`, a Tailscale OAuth client whose only scope
    is writing auth keys for the tag `tag:harness`;
  - `TRUENAS_API_KEY`.
- **Which repository and which environment are settings.** The environment's name defaults
  to `Prod`. Neither the repository's name nor anything else that identifies the Engineer's
  infrastructure is written into the harness or into a project.
- **Infrastructure work runs as GitHub Actions workflows in that repository:** the hosting
  site, Tailscale keys, and every change to the NAS for a project. A session with the
  Engineer starts them with `gh workflow run`, from any machine.
- **The repository is private,** because the run logs of a public repository are public.
  Host names, network names and dataset paths may therefore appear in its logs, and nowhere
  else.
- **No agent ever reads, prints or carries a secret.** A workflow gets its secrets from the
  environment; a command that needs a short-lived token passes it on without showing it.
- **Nothing secret or identifying is written to a repository:** no token or key, and no
  host name, tailnet name, address of the NAS or dataset path. That holds for the private
  infrastructure repository's files too; such values live in the environment's secrets and
  on the NAS.
- **The repository's files are generated by the harness and stay thin:** workflows that call
  the harness's reusable ones at a pinned tag. The logic is in the harness, where it is
  tested (G-0015).

# Rationale

A secret that no machine and no agent holds can't leak from one. GitHub already knows who
the Engineer is, masks secrets in logs, and lets a workflow be started from anywhere, so the
Engineer is no longer tied to one machine. A private repository that only the Engineer can
reach is also the lock: whoever can't start its workflows can't touch the infrastructure.
Keeping its files generated means the infrastructure repository never becomes a second place
where logic lives.

# Consequences

- Only an account with write access to the private infrastructure repository can create or
  change infrastructure. A Requester's session can't, whatever it tries.
- Infrastructure work needs GitHub to be reachable, and uses the account's Actions minutes
  for the parts that run on GitHub's own runners.
- The workflows there run code from the harness at a pinned tag with the secrets in reach:
  a harness tag is never moved, and the pin is bumped by a pull request like any update.
- What a workflow did is read from its run, with `gh run view`; an agent may read those
  logs but never copies a host name, a path or an address from them into a repository.
- A new secret is added by the Engineer, by hand, in the environment's settings.

# Guidance for agents

- Never ask for a secret, never read one from a file or the environment into your output,
  and never put one on a command line that is logged.
- To change infrastructure, start the workflow that does it; don't call the outside service
  yourself.
- Check that a secret exists by its name only (`gh secret list --env <environment>`).
- Never write a host name, a tailnet name, an address of the NAS or a dataset path into a
  commit, a pull request, an issue, a task or a decision.
- If a workflow needs a secret or a scope that isn't there, raise it for the Engineer
  (G-0010); don't work around it.
